# 03 准备重点：功能技术文档

> 状态：首版设计，尚未实现。以已确认岗位与经历生成可执行练习建议；本模块数据和接口以[数据与接口概要](../data-and-interfaces.md)为准。

## 1. 目标与用户需求

帮助应届生从“看过 JD、整理过简历”进入“知道下一步练什么”。准备计划需要说明岗位看重哪些能力、已有哪段经历可以讨论、哪些事实尚未讲清，以及为什么推荐某项练习。它是面试准备导航，不是职业测评或招聘匹配分数。

学生通常缺少完整经历与量化结果。系统应把缺口转换成可填写问题或通用练习，不能为了让计划显得完整而编造项目、技能和业绩。首版按当前目标岗位生成短计划，不建设长期课程平台或个性化教学理论引擎。

## 2. 首版范围与交互流程

1. 学生确认 `JobTarget`，选择已经确认的 `Experience`；也允许不选择经历。
2. 系统读取岗位要求与材料快照，生成“岗位重点—可讨论经历—待补充事实”关联表。
3. 展示最多三项首轮练习重点，每项解释推荐原因和练习目标；其余主题放在可展开列表。
4. 学生可切换练习重点、补充事实，或直接进入教学练习/模拟面试。
5. 岗位、经历或评价标准更新后，提示计划需更新；学生确认重新生成，不静默覆盖当前选择。
6. 完成训练后，反馈模块提供下一项建议，学生可以据此更新计划并重练。

首轮默认先准备可讲述的个人经历，再覆盖未提供证据的岗位要求；学生可以主动选择其他主题。计划显示“材料缺口”与“回答表现问题”的区别：未提供数据分析经历不能直接标为数据分析能力差。

## 3. 输入输出与数据

| 输入/输出 | 内容 | 约束 |
| --- | --- | --- |
| 岗位输入 | 已确认岗位修订、要求条目、原文与知识引用 | 继承岗位模块对明确要求与推断的区分 |
| 经历输入 | 已确认经历修订、职责、行动、结果、未知项 | 未确认解析候选不进入匹配 |
| 可选训练输入 | 既有报告中可追溯的问题与改进建议 | 有回答证据才描述表现，不用孤立模型分数排序 |
| `PreparationPlan` | 重点主题、经历关联、事实缺口、练习动作和推荐原因 | 引用输入版本，保存生成依据与学生选择 |
| 输出状态 | 计划有效/需更新、可开始的练习 | 版本过期可查看，启动新训练前重新确认有效输入 |

关联表达使用“已有相关材料”“材料不完整”“暂未提供相关材料”。这些描述属于材料覆盖，不构成能力等级。计划不保存虚构匹配率、不输出录用概率。需要补充的事实以问题呈现，例如“你亲自执行了哪些步骤”，而不是把建议填成已完成行动。

## 4. 处理逻辑与技术方案

**确定输入快照。** 服务端先检查用户归属和确认状态，读取岗位修订、选择的经历修订、知识与评价标准版本。生成过程中资料发生修改时，结果仍关联原快照，并显示需更新，避免计划与材料不一致。

**需求到证据的映射。** 程序提供岗位要求和可用经历标识，模型提出关联及其原文依据。结构校验器确认返回的岗位条目、经历和引用均属于当前输入。对技能或专业经验的关联使用保守规则：校园签到经历可以作为活动执行材料，不能因此推断独立 SQL 能力或跨部门商业项目经验。

**缺口与建议生成。** 缺口分为未提供经历、职责不清、行动不清、结果不清、岗位理解待澄清。对应动作分别为补充材料、澄清个人职责、练习行动描述、核对已有结果、查看岗位解释。对于没有量化结果的经历，允许说明具体产物、观察或反思，不能要求添加不存在的数字。

**排序。** 首版用可解释顺序：JD 明确重点且已有可用经历的主题优先；然后是常见开场与表达组织；最后列出无材料的要求供学生选择补充。训练后的更新优先处理报告里证据明确、能通过一次练习改善的问题。模型给出解释，程序限制首轮重点数量和可用主题，不采用不可解释的匹配分值。

**角色与检索。** 岗位顾问整理要求，教练评估角色将证据缺口转为动作；编排器顺序调用，不做自主角色协商。RAG 提供已发布的教学方法和题目主题，程序把计划条目链接到已存在的练习入口。模型不可凭空生成可执行路由或未维护题目。

## 5. 接口与模块依赖

| `/api/v1` 接口能力 | 输入 | 输出与依赖 |
| --- | --- | --- |
| `POST /preparation-plans` | 岗位目标、选定经历、可选报告 | 生成当前用户计划；依赖确认事实、知识检索与模型适配层 |
| `GET /preparation-plans/{id}` | 计划标识 | 计划内容、推荐原因、输入版本和是否需更新 |
| `PATCH /preparation-plans/{id}` | 学生选择的重点或顺序 | 保存偏好；不能把建议改写为个人事实 |
| `POST /sessions` | 计划主题、模式、岗位及经历快照 | 创建 `Session`，明确 `guided` 或 `mock` |

重新生成创建可追溯的计划版本，具体动作与公共接口一致。准备计划依赖岗位理解和个人材料模块；教学练习读取主题、练习目标与经历标识；反馈与重练可以生成新的准备建议，但不能替学生确认经历。

## 6. 异常与边界

- **没有经历：** 提供岗位理解、自我介绍要素整理与经历补充入口；报告不输出个性化能力结论。
- **仅有未确认候选：** 提示先确认或选择通用练习，不在后台绕过确认。
- **一个经历对应多个要求：** 允许复用，明确每个关联需要说明的具体动作，避免同一段空泛回答重复覆盖全部要求。
- **专业要求缺少可用题目：** 标为需补充内容，不用通用问答伪装为专业评测。
- **材料/岗位更新：** 旧计划保持可读并提示过期；更新计划或重新确认有效输入后开始新训练，不能继续使用已取消确认的经历。
- **生成失败：** 保留已有计划和学生选项，允许重试；可直接从已维护主题开始练习。
- **历史报告被删除：** 解除其作为新建议依据的引用，不保留无法解释的结论；统一删除规则控制派生数据处理。

## 7. 贯穿示例

小林的初级产品运营 JD 包含活动执行、基础数据分析、跨团队协作。确认经历是校园读书活动中负责报名表、签到和群提醒，60 人报名、45 人到场。

计划将“活动执行”关联到该经历，推荐先练“讲清个人动作与结果”。“基础数据分析”显示“已有报名与到场数据，可解释指标；暂未提供独立 SQL 分析经历”，不写成“具备数据分析能力”。“跨团队协作”显示具体协作对象与过程尚未提供，建议补充；不自动添加协调多个部门的故事。

首项教学练习针对小林的回答“我负责组织活动，效果很好”，引导其讲清报名表、签到和提醒。学生完成后，计划可建议换一个类似问题再讲述这些事实，检验表达迁移；不因一次更流畅的回答就宣称能力等级提升。

## 8. 验收条件

| 场景 | 可验证结果 |
| --- | --- |
| 明确 JD 与三段确认经历 | 每个推荐都能追溯岗位要求与相关经历，首轮不超过三项 |
| 有团队结果、无个人动作 | 缺口标为职责/行动待澄清，不给出“领导力强”的结论 |
| 有人数、无 SQL 经历 | 可推荐指标讲述，不新增 SQL 熟练度或项目事实 |
| 无简历、无经历 | 仍可开始通用练习，材料不足说明清楚 |
| 更新岗位或取消经历确认 | 计划提示需更新；新会话不会隐式沿用已失效事实 |
| 模型返回未知经历或题目标识 | 校验拒绝错误关联，不生成失效练习入口 |
| 报告只包含笼统评分 | 不将分数转成能力结论或新的个人事实 |
| 切换首轮重点后刷新 | 学生选择被保存，生成失败不会重置选择 |

人工检查关联准确性与建议可执行性，试用检查学生能否说明“下一步练什么、为什么”。成功标准与阶段门槛见[评测与迭代计划](../evaluation-and-roadmap.md)。

## 9. 优先级与后续扩展

P0-T 完成岗位—经历关联、缺口说明、三项重点、练习入口和版本更新提示，并将证据充分的反馈转为下一项建议，支撑文本训练与重练闭环；P1 优化推荐排序与更多可选主题。长期课程、跨岗位迁移、行业专项能力路径后续评估，不作为首版教学有效性的前提。

总体产品目标见[需求分析](../requirements.md)，角色职责与上下文策略见[知识库与智能体设计](../knowledge-and-agent.md)。
