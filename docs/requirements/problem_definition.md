# InterviewLab 第一周问题定义与产品描述

版本：v0.1 · 日期：2026-10-05 · 交付阶段：课程第一周，项目定义与仓库构建。

> 本文是第一周 5W1H 报告与产品描述。当前项目处于规划阶段，尚无可运行应用、用户访谈记录或教学效果实测结果。用户需求、性能目标和技术选型均需在后续开发与试用中验证；本文不将设计假设写成已证实结论。

## 1. 产品描述

**InterviewLab（面试练习室）是面向应届生的自主 AI 面试教学 Web 应用。** 学生围绕目标岗位和自己确认的真实经历，完成岗位理解、教学练习或模拟面试、证据反馈、单题重练与回答对比。首版最终体验计划采用中文实时语音与一位风格化 3D 虚拟面试官，先交付可验证的文本教学闭环，再逐步加入语音和角色。

产品希望帮助学生回答三个具体问题：目标岗位要求我做什么；我的哪些真实经历能说明相关能力；我怎样将职责、行动与结果讲清楚。系统的核心输出是基于本次回答的具体改进建议与重练任务，不输出录用概率、招聘筛选结论或标准化的“完美履历”。

| 项目要素 | 当前定义 |
| --- | --- |
| 产品名称 | InterviewLab · 面试练习室 |
| 主要用户 | 准备实习或初级岗位面试的应届生，覆盖不同专业 |
| 核心问题 | 岗位要求理解不充分、个人经历表达不具体、缺少能够连续追问和给出可执行反馈的练习对象；这些是待验证的需求假设 |
| 使用方式 | 学生自主在 Web 应用中练习；首版采用受邀学生账号 |
| 主要输入 | 岗位模板或自带 JD、学生确认的简历/经历、训练回答 |
| 主要输出 | 岗位解读、准备主题、逐字稿、分维度证据反馈、重练对比及个人训练历史 |
| 首个可运行里程碑 | 文本流程可以从岗位选择走到反馈、重练与历史回顾 |
| 首版完整目标 | 在文本闭环基础上加入中文语音和 3D 角色，并完成小规模试用 |
| 当前交付 | 问题定义、需求和技术规划、仓库与团队协作配置；不含已实现功能 |

详细需求及编号见[需求分析](../requirements.md)。

## 2. 5W1H 问题定义

### What：要解决什么问题？

学生准备面试时，可能只记住岗位关键词或泛泛介绍项目，却不能说明工作任务、自己的个人贡献和结果依据。例如，“我负责组织活动，效果很好”没有交代具体职责，也没有给出结果信息。一次固定题目练习或没有原文依据的笼统评价，难以告诉学生下一轮应具体改变什么。

本项目围绕“理解岗位 → 整理真实经历 → 回答与追问 → 查看证据反馈 → 重练与对比”建立教学闭环。首版覆盖自我介绍、项目/实习/校园经历、行为问题及基于材料的岗位理解，聚焦可观察的表达和理解，不判定跨行业专业资格或高级技术能力。

### Why：为什么值得解决？

当前产品设计的判断是：学生需要可重复使用的练习机会，以及与自己的回答和岗位目标相关的具体反馈。若系统能够追问缺失信息、引用回答原文并给出一个可执行的练习任务，就可能降低开始练习的门槛，并帮助学生把已有经历表达得更清楚。

这些价值目前属于产品假设。仓库没有证据证明学生普遍存在上述困难，也没有证据证明 AI、语音或 3D 已改善面试表现。后续需通过访谈、流程试用、人工评阅和同类新题检验判断需求是否成立、建议能否执行、改进能否迁移；满意度或模型分数上涨不能独立证明教学有效。

### Who：为谁解决，由谁参与？

| 对象或角色 | 需求或职责 |
| --- | --- |
| 初次准备面试的应届生 | 理解 JD 中的职责与要求，确定自我介绍和练习重点 |
| 有经历但表达困难的应届生 | 区分团队成果和个人行动，补充已知结果及证据 |
| 已有面试经验、需要改进的应届生 | 定位本次回答的问题，专项重练并观察变化 |
| 内容与运行维护人员 | 审核知识和题库、维护权限、处理故障与费用；不作为教师端教学用户 |
| 项目小组 | 分担需求与内容、前后端、AI/语音、3D、测试和项目管理职责；具体人员由小组确认 |
| 课程教师 | 通过仓库、文档和 Issues 检查交付并提供第一轮反馈 |

前三类用户画像是设计假设，不代表已访谈的真实用户。首版只有学生教学用户，不建设教师端、班级管理或课程作业功能。小组成员、GitHub 账号与负责人分配统一记录在[团队计划](../mgmt/team_plan.md)，本文不编造姓名或已完成分工。

### When：何时使用，何时交付？

学生可以在确定目标岗位、准备某次面试前使用，也可以在面试后针对自我介绍、经历表达等薄弱点开展专项练习。模拟面试目标时长为 5～10 分钟；专项教学允许单题提示和重答，具体时长与资源上限按需求及评测文档实现。

课程第一周交付项目定义、规范 README、目录骨架、分支和协作管理，并在第一周结束前提交仓库链接，通过 Issues 获取第一轮反馈。课程起止日期和教师规定的具体截止时间尚未提供，由小组在[第一周提交清单](../mgmt/week1_submission.md)中核对，2026-10-05 是本文编写日期，不等同于课程截止日。

后续按 A 文本闭环、B 语音闭环、C 3D 交互、D 小规模试用推进，阶段验收通过后再进入下一阶段。具体开发日期需要团队人数、分工、预算和服务接入条件，当前不作未经确认的工期承诺。阶段定义见[评测与迭代计划](../evaluation-and-roadmap.md#6-开发阶段与门槛)。

### Where：在什么环境中使用与协作？

学生计划通过 Web 浏览器在宿舍、家中等便于自主练习的环境中使用。语音练习需要麦克风及适合说话的环境；没有麦克风权限、语音故障或设备性能不足时，仍能通过文本和静态头像继续训练。首版语言为中文，网络和浏览器兼容范围在原型验证后确认。

代码、文档、任务与反馈在 GitHub 仓库中协作，任务状态通过看板和 Issues 追踪。真实简历、录音、个人训练记录和 API 密钥不提交到仓库；开发示例使用合成材料或明确获授权的数据。未来部署地址、服务器和云服务商尚未确定。

### How：怎样解决与验证？

1. 学生选择岗位模板或粘贴 JD，系统区分原文要求、知识解释和推断。
2. 学生上传简历或手动填写经历，确认可用事实；材料不足时可补充或进入通用练习。
3. 系统关联岗位要求与经历，学生选择准备主题及教学练习/模拟面试模式。
4. 教学模式允许分步提示与即时反馈；模拟模式围绕回答动态追问，结束后集中反馈。
5. 报告在表达结构、岗位理解和经历证据三个维度提供观察，引用回答原文；未触及或证据不足的内容标记为未观察。
6. 学生针对一个问题重练，同时查看原回答、新回答和变化说明，保存或删除个人记录。

实现方案暂考虑 Next.js + TypeScript、PostgreSQL + pgvector、LLM/ASR/TTS 服务适配层、确定性会话编排与受控检索，以及 Three.js + VRM 角色。上述方案均未锁定、未实现，服务商须依据统一样例比较质量、延迟、网络可用性和实际费用。模块关系见[总体技术架构](../architecture.md)，验证方式见[评测与迭代计划](../evaluation-and-roadmap.md)。

## 3. 典型使用场景

### 场景一：有目标岗位，但不知道准备什么

学生选定初级岗位并粘贴 JD，希望理解工作任务和能力要求。系统解释岗位要求、保留来源并关联学生已确认的经历，生成可选训练主题；没有经历证据的要求说明材料缺口，不推断学生一定不具备能力。

### 场景二：做过项目，但说不清个人贡献

以下是仓库共用的合成示例，不是真实访谈或实验结果：小林目标为初级产品运营，曾在校园读书活动中负责报名表、签到和群提醒；60 人报名、45 人到场。首次回答“我负责组织活动，效果很好”后，系统追问具体工作和结果，反馈指出原回答缺少行动与结果信息。

小林重练时补充已知职责和人数，系统说明回答更具体，但不能添加 SQL 技能、解释为业务增长，或将所有活动结果归因于小林。该场景用于验证真实事实边界和反馈到重练的数据衔接。

### 场景三：练习中遇到故障或希望提前结束

学生拒绝麦克风权限、发生语音故障或角色加载失败时，仍可用文本继续。学生主动结束时，保存已确认的有效回合，并根据已有证据提供反馈；没有回答的维度标记为未观察，不生成无依据评价。

## 4. MVP、首版范围与边界

**最小可验证产品（MVP）首先交付阶段 A 的文本教学闭环。** 语音与 3D 是首版完整体验的后续必需目标，不因先做文本而被取消。所有功能目前都处于待实现状态。

| 范围 | 计划交付 |
| --- | --- |
| 阶段 A：文本 MVP | 受邀账号与记录隔离、岗位/JD 解读、材料解析与确认、经历手填、准备主题、教学/模拟两种模式、动态追问、证据报告、单题重练与对比、历史与删除、内容维护与费用监测 |
| 阶段 B：语音闭环 | 中文识别、字幕确认、流式语音、用户打断、断线恢复和文本降级 |
| 阶段 C：3D 交互 | 一位风格化半身角色，待机/倾听/思考/说话状态、实际播放音频驱动嘴型和静态降级 |
| 阶段 D：小规模试用 | 学生自主完成流程，记录障碍、人工反馈、迁移表现及语音/3D 的体验价值 |
| 首版暂不包含 | 教师端、班级管理、实时招聘搜索、自动投递、支付、写实视频数字人、摄像头情绪识别、实时算法 IDE、专业能力认证、排名和录用概率 |

反馈采用有描述锚点的 1～4 档及 `not_observed`，不合成加权总分。示范表达只基于已确认事实；不得替学生编造经历、数字、技能或因果关系。功能优先级和编号以[需求分析](../requirements.md#4-功能需求与优先级)为准。

### 第一周交付验收

| 验收项 | 完成证据 |

| 仓库可审阅 | README 说明定位、当前状态、文档入口、目录、协作与后续开发计划；教师能够访问仓库 |
| 工程与协作建立 | 课件要求的目录和分支策略有明确记录；任务具备负责人确认入口、期限和验收条件；看板可展示状态 |
| 链接提交与第一轮反馈 | 按课程要求提交仓库链接，使用 Issues 留存请求与反馈；尚未收到反馈时保持待完成状态 |

第一周是否完成以[提交清单](../mgmt/week1_submission.md)的实际记录为准。本文不将计划中的看板、已请求的评阅或拟议任务写成已完成反馈。

### 后续产品验收

- **流程**：学生能够完成岗位 → 确认材料 → 练习/模拟 → 反馈 → 重练 → 历史回顾；无材料、提前结束和服务失败有可继续路径。
- **证据与事实**：报告原文引用能定位到回答版本，建议有依据；不得添加未确认个人事实，未观察项不能硬评分。
- **数据**：账号之间不能访问彼此的材料和记录；删除能清理关联材料、快照、报告和任务；密钥保存在服务端。
- **语音与角色**：测量转写、打断和分段延迟；角色状态与实际音频一致，故障与弱设备场景能降级。
- **教学效果**：观察建议可执行性和重练情况，并由人工评阅比较无提示前后回答及同类新题；不以模型自评或满意度代替学习证据。
- **运行成本**：统计完整旅程、失败重试与重练的实际用量和费用，核对账单后确定预算上限。

量化门槛、评测集和阶段进入条件集中维护在[评测与迭代计划](../evaluation-and-roadmap.md)，上述指标当前均没有实测结果。

## 6. 待验证假设与下一步

| 假设 | 需要收集的证据 | 可能影响的决策 |
| --- | --- | --- |
| 学生愿意提供并确认材料 | 访谈、确认耗时、跳过/退出原因及事实纠错记录 | 缩减确认步骤，强化手填与通用训练 |
| 岗位解读有助于选择准备重点 | 学生能否解释岗位任务并选择相关经历，记录困难与误解 | 调整解读结构、范围或知识内容 |
| 原文证据和具体建议能促成重练 | 建议理解度、能否执行、反馈查看后的主动重练及重练原因 | 减少泛泛建议，优先呈现一项练习任务 |
| 改进能迁移到同类新题 | 人工盲评不同但同类题目的回答，区分提示和新增事实 | 修订教学方法，避免只训练记忆同一个答案 |
| 语音收益足以覆盖识别与等待负担 | 转写纠错、延迟、打断成功与完成率 | 调整语音提供商或文本入口 |
| 3D 角色有额外体验价值 | 相同语音/题目下静态头像与 3D 的比较，记录分心、疲劳和重练选择 | 决定角色呈现方式及后续投入 |
| 服务质量与费用可接受 | 统一样例结果、代表性训练用量、账单与故障记录 | 确认技术方案、预算和阶段排期 |

下一步先完成小组成员和分工、截止日期及看板状态的确认，再开展合成材料演练与需求验证。未确认的人员、日期、供应商、预算和反馈结果由管理文档持续记录，不写成已落实事实。
